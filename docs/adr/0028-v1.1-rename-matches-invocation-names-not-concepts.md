# The v1.1 rename matches invocation names, not concepts

**Status:** Extends ADR-0004 (fork only on glossary pollution) and ADR-0008 / ADR-0011
(the unit of work is an **Issue**, the artifact is a **PRD**).

Matt Pocock's upstream skills were renamed in v1.1: `to-prd` → `to-spec` and
`to-issues` → `to-tickets`. This repo's `strategic-planning` skill invoked the old names,
so the invocations no longer resolve. This ADR records how we reconciled the rename with a
glossary that deliberately says **PRD** and **Issue** (never "spec" or "ticket").

**Decision:** sync the **invocation names only** — `strategic-planning` now calls `to-spec`
and `to-tickets` by their real v1.1 names — and change **nothing** about the glossary. The
artifacts stay a **PRD** and **Issues**; "spec" and "ticket" remain `_Avoid_` terms
(CONTEXT.md, ADR-0008). This is a name-match, not a re-ruling.

Why a rename and not a fork: ADR-0004's fork trigger keys on a skill's **output
vocabulary** polluting the glossary, not on its name. The v1.1 skills **defer to the
project glossary**, so their output does not pollute — nothing triggers a fork. Renaming
the references is the whole change; forking would add upstream divergence for no payoff.

Two behaviours are pinned to our concepts rather than the skills' upstream defaults, via a
**Naming boundary** note in `strategic-planning/SKILL.md` (option A1):

1. `to-spec` upstream *publishes a spec to the tracker*; we override that to **write a PRD
   file** to `.agents/prds/{name}.prd.md`. That file node is load-bearing — `/plan` consumes
   it and Alignment history references it — so it is kept, not dropped.
2. `to-tickets` needs no behavioural override: it already **converges** on our concept,
   publishing real GitHub Issues labelled `ready-for-agent` — exactly the **Issue** unit
   (ADR-0011). The boundary note only pins the name (unit = Issue, not "ticket").

Concretely changed: `strategic-planning/SKILL.md` (five references + the boundary note),
`CONTEXT.md` (the factual producer name in the **Issue** entry: `to-issues` → `to-tickets`),
and `README.md` (the non-vendored-skills note). The glossary **concepts** — the **PRD** and
**Issue** entries and their `_Avoid_` lines — are untouched.

Alternatives rejected:
- **Follow upstream fully** (adopt "spec" / "ticket" vocabulary) — re-pollutes the glossary
  that the ADR-0008/0011 sweep just cleaned, reintroducing the one-thing-two-names the
  project forbids. The motivation was explicitly to match invocation names, not concepts.
- **Fork `to-spec` / `to-tickets` into this repo (the ADR-0004 remedy)** — the fork trigger
  is output-vocabulary pollution, and these skills defer to our glossary, so there is
  nothing to fork; a fork would only add divergence to maintain.
- **Drop the PRD-file node and let `to-spec` publish to the tracker** — discards the
  `.agents/prds/{name}.prd.md` artifact that `/plan` and the Alignment record depend on.

Consequence: the invocation names now match upstream v1.1 while the concepts and storage
model stay **PRD-file → GitHub Issue**. The only divergence from upstream defaults is
`to-spec`'s file-vs-tracker output, pinned in the `strategic-planning` boundary note — not
in the glossary, which remains the single source of the project's vocabulary.
